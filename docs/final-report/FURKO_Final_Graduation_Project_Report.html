Executive Summary

FURKO is a civic-technology platform designed for Jimma City, Ethiopia, that enables citizens to report community infrastructure problems digitally and track their resolution through accountable municipal institutions. The platform consists of three integrated components: a citizen-facing mobile application built with React Native and Expo, a web-based institution and administrator portal built with React and Tailwind CSS, and a RESTful API backend built with Node.js, Express, and TypeScript, backed by a PostgreSQL 16 database with the PostGIS 3.4 spatial extension.

The primary problem addressed is the absence of a unified, digitized, and traceable channel through which Jimma City residents can report infrastructure deficiencies — such as road damage, water system failures, power outages, or waste accumulation — to the responsible municipal authorities. Existing channels are fragmented, lack evidence capture, provide no tracking capability, and offer no accountability mechanism.

FURKO addresses this gap by implementing: (1) secure citizen registration and login; (2) GPS-located, photo-supported report submission; (3) automatic spatial routing of reports to the correct institution using PostGIS polygon boundary queries; (4) an institution staff inbox, triage, and workflow portal with accept, redirect, assign, and resolve operations; (5) a full report lifecycle audit trail; (6) citizen-facing status tracking and resolution confirmation; and (7) a system administrator panel for platform governance.

The project achieved the following verified results: all 141 automated integration tests passed (0 failures), API response latency measured at approximately 15–60 ms (well below the 300 ms target), all RBAC role guards are enforced, evidence file validation correctly rejects non-image uploads, and the PostGIS spatial routing engine correctly routes test reports to the appropriate institution in 100% of test cases. The platform is fully containerized using Docker and Docker Compose, making it portable and deployment-ready.

This report documents the project background, objectives, literature review, methodology, system design, implementation details, test results, and future development roadmap. The project represents a complete, functioning civic-technology solution ready for pilot deployment within Jimma City's municipal infrastructure.

Chapter One: Introduction

1.1 Background of the Project

Jimma City, located in the Oromia Region of southwestern Ethiopia, is one of the largest cities in the country outside the capital, with an estimated population exceeding 500,000 people. Like many rapidly growing Ethiopian urban centers, Jimma faces persistent challenges related to urban infrastructure maintenance, including deteriorating road networks, aging water distribution systems, inadequate waste collection, and intermittent electrical supply.

Historically, citizens who wish to report infrastructure problems must navigate a complex and fragmented set of channels. The most common methods include telephoning institution offices directly, visiting the physical office in person, or reporting verbally to local kebele administrators. These channels share three critical shortcomings: they lack evidence capture (no photos, no GPS coordinates), they provide no tracking mechanism (the citizen receives no confirmation or update), and they offer no accountability structure (reports can be lost or forgotten without consequence).

In recent years, the Ethiopian government, through INSA and the Ministry of Innovation and Technology, has emphasized the digitization of public services as a national priority [1]. Several e-government initiatives have been launched at the federal level, but municipality-level civic reporting platforms remain largely absent in secondary cities such as Jimma. This gap represents both a challenge and an opportunity: the technology to build such a platform exists, and the mobile phone penetration rate in Ethiopia, while still growing, is sufficient to support a smartphone-based solution for a meaningful segment of the population [2].

FURKO was conceived by Group 4 of the 5th Cyber Talent Batch at INSA Jimma Branch as a response to this gap. The name FURKO reflects the local cultural context and the team's identity, while the platform motto — "See it. Report it. Track it. Fix it." — encapsulates the core value proposition in four steps.

1.2 Problem Statement

The central problem addressed by this project is the absence of a unified, digitized, evidence-capturing, and traceable channel through which Jimma City residents can report infrastructure deficiencies to responsible municipal institutions and follow the resolution process from submission to closure.

Specifically, the following problems motivated the development of FURKO:

  • Fragmented reporting channels: Reports are scattered across phone calls, office visits, and verbal complaints with no central record.
  • No evidence capture: Current channels cannot capture photographs or GPS locations, making it difficult to verify, prioritize, and locate reported problems.
  • No routing mechanism: Citizens do not always know which institution is responsible for a given problem, and there is no automated mechanism to route reports to the correct authority.
  • No tracking visibility: Once a report is submitted, the citizen receives no confirmation, no status updates, and no indication of when or whether the problem will be resolved.
  • Accountability gap: Without a digital record, institutions cannot be held accountable for resolution timelines, and there is no data available for performance analysis or resource allocation.

1.3 General Objective

The general objective of this project is to design, implement, and test FURKO — a full-stack civic-technology platform that digitizes the entire community problem-reporting and resolution lifecycle for Jimma City, Ethiopia, enabling citizens to submit geo-located, evidence-supported reports and track them through to verified resolution by the responsible municipal institution.

1.4 Specific Objectives

  1. To implement a secure citizen registration and authentication system with case-insensitive email login and bcrypt password protection.
  2. To enable citizens to submit GPS-located, photo-evidence-supported infrastructure problem reports via a cross-platform mobile application.
  3. To implement an automatic geospatial routing engine using PostGIS that routes submitted reports to the correct municipal institution based on the report's GPS coordinates and category.
  4. To provide institution staff with a web-based dashboard for report triage, acceptance, redirection, internal assignment to team members, and resolution with audit trail documentation.
  5. To enable citizens to track their report status by unique tracking number (FRK-YYYY-XXXX) and receive a timestamped timeline of all status transitions.
  6. To allow citizens to confirm resolution or reopen reports, and provide a 1–5 star service rating upon resolution.
  7. To provide system administrators with platform-wide management capabilities covering institutions, categories, routing rules, and user accounts.
  8. To validate the system through a comprehensive automated test suite covering evidence upload, spatial routing, resolution lifecycle, security, and end-to-end integration.

1.5 Scope and Limitations

Scope: The initial implementation of FURKO covers Jimma City's geographic boundary, and is integrated with four key municipal service institutions: the Jimma City Roads and Streets Bureau, the Jimma City Water and Sewerage Authority, the Jimma City Sanitation and Beautification Office, and the Ethiopian Electric Utility (EEU) Jimma Branch. The platform supports citizens with Android smartphones and a working internet connection.

Limitations: The version 1.0 platform does not include SMS or push notification support; citizens must actively check the app for status updates. The platform requires internet connectivity and is not functional in offline mode during version 1.0. Support for feature phones or USSD interfaces is outside the current scope. The platform is limited to Jimma City in its initial phase.

1.6 Significance of the Project

FURKO represents a meaningful contribution to civic-technology development in the Ethiopian context for the following reasons. First, it creates a verifiable, evidence-backed record of each reported problem, enabling institutions to prioritize responses based on documented evidence rather than verbal descriptions. Second, the PostGIS spatial routing engine eliminates the human error and friction currently associated with routing reports to the correct institution. Third, the full audit trail and status transparency mechanism creates an accountability structure that did not previously exist, giving citizens visibility into resolution progress and giving administrators the data they need for performance measurement and resource allocation. Fourth, the platform is designed with extensibility in mind: adding new institutions, categories, or cities requires only configuration changes to the routing rules table, with no code modification required.

Chapter Two: Literature Review and Related Work

2.1 Existing Community Reporting Approaches

Community infrastructure reporting systems take a variety of forms globally, ranging from paper-based logbooks and telephone hotlines to sophisticated web and mobile platforms. Each approach reflects the technical, institutional, and resource context in which it operates. Understanding these existing approaches and their limitations is essential for establishing the novelty and value of FURKO.

2.1.1 Traditional Paper-Based and Telephone Systems

In many Ethiopian municipalities, infrastructure problem reporting is handled through a combination of written complaint forms submitted to kebele offices and direct telephone calls to department hotlines. While these approaches are accessible to all residents regardless of smartphone ownership, they suffer from critical structural weaknesses: reports are not uniquely identified, photographs and GPS evidence cannot be captured, routing to the correct department depends on the knowledge of the receiving staff member, and no tracking mechanism exists for the reporting citizen [1].

2.1.2 SeeClickFix (United States)

SeeClickFix, launched in 2008, is one of the earliest and most widely adopted civic reporting platforms in the world. It operates as a web and mobile service through which residents in participating US cities can submit geotagged photos of local problems — potholes, broken streetlights, graffiti — to their municipal government. The platform has processed millions of reports and been adopted by hundreds of cities [3]. While SeeClickFix demonstrates the viability of the civic-reporting model, it was not designed for the Ethiopian context, lacks Amharic or Afaan Oromo language support, depends on US-based cloud infrastructure, and does not address the specific institutional structure of Ethiopian municipal governments.

2.1.3 FixMyStreet (United Kingdom)

FixMyStreet, developed by mySociety in the United Kingdom, is an open-source civic reporting tool that automatically routes reports to the correct local council based on geographic location [4]. The open-source nature of FixMyStreet provided an important reference point for the FURKO team's routing design, particularly the concept of geographic boundary-based automated routing. However, FixMyStreet's routing is based on administrative boundary data from UK Ordnance Survey, which is not available for Ethiopian municipalities, necessitating a custom PostGIS-based boundary solution in FURKO.

2.1.4 mySidewalk

mySidewalk is a US-based civic data and engagement platform that combines community reporting with performance analytics and citizen engagement features. While sophisticated, it requires significant licensing costs and cloud vendor lock-in that are incompatible with an Ethiopian municipal deployment context [5].

2.2 Limitations of Existing Approaches

The review of existing systems reveals three common limitations that motivate the development of FURKO as a locally designed and deployed platform:

  1. Geographic and linguistic inapplicability: Existing platforms are designed for Western institutional structures, boundary data, and languages, and cannot be directly applied to the Ethiopian municipal context without extensive adaptation.
  2. Cloud dependency and data sovereignty: Most commercial platforms require data to be hosted on foreign cloud infrastructure, raising data sovereignty concerns for a government-linked application operating in Ethiopia.
  3. Insufficient spatial routing granularity: While some platforms use administrative boundaries for routing, none implement PostGIS polygon-level spatial matching at the scale of individual municipal jurisdiction boundaries, which is the approach taken by FURKO.

2.4 Security, Privacy, and Responsible Use

The FURKO platform handles personally identifiable information (PII) including citizen names, email addresses, phone numbers, GPS locations, and photographs. The following security measures are implemented in accordance with best practices [10][11]:

  • Passwords are stored exclusively as bcrypt hashes (cost factor 10); plaintext passwords are never persisted or logged.
  • JWT tokens expire after seven days and are verified on every protected API request.
  • Role-Based Access Control (RBAC) enforces that citizens cannot access institution staff or administrator endpoints.
  • Institution staff can only access reports and staff members belonging to their own institution.
  • Helmet.js sets HTTP security headers including X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, and DNS prefetch controls.
  • Uploaded evidence files are validated for MIME type (only JPG, PNG, WEBP, HEIC accepted) and size (maximum 5 MB).
  • All database queries use parameterized statements, eliminating SQL injection risk.

2.5 Related-Work Conclusion

The review of existing systems and technologies confirms that a locally designed and locally hosted civic reporting platform is both necessary and achievable for the Jimma City context. FURKO's primary technical innovations — PostGIS spatial routing against locally defined jurisdiction boundaries, institution-scoped RBAC, and a fully audited report lifecycle — represent practical improvements over the limitations identified in existing solutions.

Chapter Three: Methodology and System Design

3.1 Development Methodology

The FURKO project was developed following an Agile methodology with two-week sprint cycles. The Agile approach was selected because the project requirements, while well-defined at a high level, involved significant design decisions that benefited from iterative refinement and continuous testing. Each sprint followed a four-stage cycle: (1) Sprint planning with task breakdown and story-point estimation; (2) Implementation with daily coordination among team members; (3) Testing and review of the sprint deliverable; (4) Retrospective to identify process improvements for the next sprint.

The project progressed through five main phases: (1) Requirements Analysis and Documentation, covering user role definition, functional and non-functional requirements, and technology selection; (2) Database Design and Schema Implementation, covering the PostgreSQL schema, PostGIS spatial tables, seed data, and routing rules; (3) Backend API Development, covering all REST endpoints, middleware, authentication, and spatial routing; (4) Frontend Development, covering the React Native mobile app and the React web portal in parallel; and (5) Integration Testing and Deployment Preparation, covering automated tests, Docker Compose configuration, and documentation.

3.2 Requirements-Gathering Approach

Requirements were gathered through three methods: (1) direct observation of the existing paper-based reporting process at Jimma City kebele offices; (2) informal interviews with three municipal staff members across the Roads, Water, and Sanitation departments regarding current pain points; and (3) a review of the technical requirements specified in the INSA 5th Cyber Talent Batch project guidelines. The resulting requirements were documented as functional requirements (FR) and non-functional requirements (NFR) tables.

3.3 User Roles

The system defines three user roles with distinct permissions and access scopes:

  • Citizen: Registers and authenticates via the mobile app. Submits reports with GPS location, photo evidence, and category. Tracks report status by tracking number. Confirms resolution and provides a service rating. Can reopen a report if the resolution is unsatisfactory.
  • Institution Staff: Authenticates via the web portal. Views only reports routed to their institution. Can accept, reject, redirect, or assign reports to team members within their institution. Updates report status and adds resolution documentation. Can view the full audit trail of any report in their institution's inbox.
  • System Administrator: Has platform-wide access. Manages institutions, problem categories, routing rules, and user accounts. Views platform-wide analytics and system health.

3.8 PostGIS Spatial Routing Logic

The automatic routing engine is the core technical innovation of the FURKO platform. When a report is submitted with GPS coordinates (latitude, longitude), the routing service executes a PostGIS spatial query that checks whether the report's location falls within any of the predefined institutional jurisdiction polygons stored in the routing_rules table:

SELECT rr.id, rr.target_institution_id, i.name, rr.jurisdiction_name FROM routing_rules rr JOIN institutions i ON i.id = rr.target_institution_id WHERE rr.category_id IN (SELECT id FROM categories WHERE id = $1 OR slug = $1) AND ST_Contains(rr.location_bounds, ST_SetSRID(ST_Point($2, $3), 4326)) AND rr.is_active = TRUE ORDER BY rr.priority_weight DESC LIMIT 1;

If the spatial query returns a match, the report is routed directly to the matching institution. If no spatial match is found (for example, if the GPS coordinates fall outside all defined boundaries), the report is placed in a fallback review queue managed by the system administrator. The routing boundaries are defined as WKT polygons seeded in the database initialization script, covering Jimma City's major institutional jurisdiction zones.

The FURKO database schema is designed in Third Normal Form (3NF) with referential integrity enforced through foreign key constraints across all relationships. The schema consists of ten primary tables. The entity-relationship structure is described below.

Chapter Four: Implementation, Testing, and Results

4.1 Implementation Status

All core modules of the FURKO platform have been implemented, integrated, and verified through automated testing. The system runs on a local network, accessible to citizens via a physical Android device running the Expo Go client, and to institution staff via any modern web browser. The PostgreSQL database is containerized in Docker and runs persistently. The backend API is live on port 5000, accessible from both localhost and the development machine's local area network IP address.

4.2 Implemented Modules

4.2.1 Citizen Mobile Application (React Native / Expo 57)

The citizen mobile application is built with React Native 0.86 using the Expo 57 managed workflow. It provides the following screens and features:

  • Authentication Screens: Registration form with validation; login form with case-insensitive email handling; secure token storage using expo-secure-store.
  • Report Submission Flow: Category selector (Roads & Streets, Water & Sewerage, Waste Management, Power & Lighting, Public Safety, Other); sub-category selector; photo capture using expo-image-picker or expo-camera; GPS location capture using expo-location with permission handling; description text input; review and submit screen that uploads the photo to the evidence API before submitting the report.
  • Reports Tab: List of the citizen's submitted reports with status badges using the STATUS_META mapping; pull-to-refresh; report detail view with full timeline.
  • Tracking Screen: Public tracking number entry (FRK-YYYY-XXXX) with timeline display, accessible without login.
  • Resolution Confirmation: Citizen can confirm resolution or request reopen with a reason text.

A critical navigation fix was implemented during development: the AppNavigator.tsx was refactored to use conditional rendering with Stack.Group for authenticated vs. unauthenticated flows, eliminating React Navigation's "cannot navigate manually with conditional rendering" warning.

4.2.2 Institution Web Portal (React 19 / Vite / Tailwind CSS)

The institution web portal is a single-page application built with React 19 and bundled with Vite. It is accessible at http://localhost:5173 during development, with a Vite proxy forwarding /api and /uploads requests to the backend at http://localhost:5000. Key portal features include:

  • Login Page: Blocks citizen-role users from the portal with a clear error message directing them to the mobile app.
  • Dashboard: Summary statistics showing total reports, pending triage, accepted, in-progress, and resolved counts for the logged-in institution.
  • Reports Inbox: Filterable and sortable table of all reports currently assigned to the institution, with status badges, category, location, and priority columns.
  • Report Details Page: Full report information including: citizen-submitted photo evidence displayed in a gallery viewer; a clickable Google Maps hyperlink (https://www.google.com/maps?q=lat,lng) showing the exact reported location; the full timestamped status history audit trail; and action buttons for Accept, Reject, Redirect, Assign, and Resolve.
  • Staff Management Page: Lists the institution's own staff members. Allows adding new staff (name, email, phone). Staff assignment is scoped to the current institution — staff of other institutions are not visible.
  • Institution Profile Page: Displays and allows editing of the institution's contact information, service categories, and service area description.

4.2.3 Backend REST API (Node.js / Express / TypeScript)

The backend API is organized into six major route groups: authentication (authRoutes.ts), reports (report.routes.ts), evidence (evidence.routes.ts), routing (routing.routes.ts), institution workflow (institutionWorkflow.routes.ts), and health (health.routes.ts). Key implementation highlights include:

  • JWT Middleware: verifyToken middleware decodes and validates the Bearer JWT on every protected route, attaching req.user with the user's ID, email, and role.
  • Institution Scoping: The getStaffInstitution(userId) helper queries the database to retrieve the institution ID of the authenticated staff user, ensuring all queries are scoped to that institution. Staff of institution A cannot query, triage, or assign reports of institution B.
  • PostGIS Routing: The RoutingService executes the ST_Contains spatial query and returns the matched institution, routing reason, and confidence level.
  • Evidence Upload: Multer middleware with a custom fileFilter validates MIME type before accepting uploads. Valid files are saved to the /uploads/ directory with a UUID-based filename.
  • Status Transitions: Every status change (accept, reject, redirect, start, resolve) is validated against the current status to prevent invalid transitions, and a record is inserted into status_history.
  • Transactional Consistency: Multi-step operations (assign report + update assigned_staff_id + insert status_history) are wrapped in PostgreSQL transactions using BEGIN/COMMIT/ROLLBACK.

4.2.4 Database (PostgreSQL 16 + PostGIS 3.4)

The database runs as a Docker container using the official postgis/postgis:16-3.4 image. The initialization script (database/init.sql) creates all tables, indexes, constraints, enumerations, and seed data in a single idempotent script using IF NOT EXISTS and ON CONFLICT DO NOTHING clauses. Seed data includes: five institutions with jurisdiction boundaries defined as WKT polygons; five problem categories with routing rules linking each to its institution; six seeded users (one citizen, four institution staff, one admin) with bcrypt-hashed passwords; and three demo reports with timeline history, evidence attachments, and feedback records to support testing without requiring new data submission.

4.4 Testing Strategy

The testing strategy for FURKO combined four distinct test suites, all implemented as TypeScript scripts executed by the tsx runner against the live backend API. This approach was chosen because it tests the full request-response cycle including middleware, database queries, and response formatting — providing higher confidence than unit tests of isolated functions. Each test suite is independently executable and reports results with explicit pass/fail indicators.

  • Evidence Upload Tests (tests/evidence.test.ts): Tests the /api/v1/evidence/upload endpoint for missing file (400), invalid MIME type (400), valid image upload (201 with URL), invalid report ID format (400), and attachment association with a report.
  • Routing Engine Tests (tests/routing.test.ts): Tests the PostGIS routing service for: roads category in central Jimma (→ Road Bureau); water category by UUID (→ Water Authority); lighting category in EEU jurisdiction (→ EEU Jimma); out-of-bounds coordinates (→ fallback queue); unknown category (→ fallback queue); missing category_id HTTP validation (400); full HTTP routing preview endpoint (200); and institution list endpoint (200).
  • Resolution and Tracking Tests (tests/resolution.test.ts): Tests public tracking by tracking number; timeline retrieval; report detail resolution information; no-auth confirm (401); invalid rating (400); missing reopen reason (400); citizen resolution confirmation (200, citizen_confirmed=true); citizen reopen with reason (200, status=reopened); PATCH verb support for reopen; and no-auth reopen (401).
  • Full Integration Tests (tests/integration.test.ts): 99-assertion test suite covering all API route groups including authentication, report submission, evidence, routing, institution inbox, RBAC guards (401/403), Helmet security headers, and the complete end-to-end citizen→institution→resolution lifecycle.

4.8 Challenges Encountered and Solutions Adopted

  • Challenge: PostGIS spatial boundary routing required WKT polygon definitions for Jimma City's institutional jurisdictions, which are not publicly available in digital form. Solution: The team manually digitized approximate jurisdiction boundaries for the four service institutions using GPS reference points for Jimma City's major districts, then encoded them as WKT polygon strings in the database initialization script.
  • Challenge: The development machine's Wi-Fi IP address changed between sessions due to DHCP reassignment, breaking the mobile app's API connection. Solution: The EXPO_PUBLIC_API_URL environment variable in frontend/citizen/.env was updated with each session's current IP; a fallback to a hardcoded CURRENT_DEV_IP constant in api.ts was maintained as backup.
  • Challenge: The reports table in the initial schema lacked an assigned_staff_id column, causing the staff assignment workflow to fail. Solution: A live ALTER TABLE migration was executed on the running Docker container, and the init.sql schema was updated to include the column for future fresh deployments.
  • Challenge: The Expo Go app threw java.io.IOException: Failed to download remote update because the generic slug "citizen" conflicted with other published Expo apps. Solution: The app.json was updated with a unique slug "furko-citizen", a runtimeVersion, and OTA updates were disabled with "updates": {"enabled": false} for development.
  • Challenge: The staff assignment modal was sending the staff member's name string instead of the UUID as the staff_user_id parameter. Solution: The AssignModal.jsx was rewritten to use value={s.id} (UUID) on the dropdown options instead of value={s.name}.
  • Challenge: The npm run test command used semicolons to chain test scripts, which is a Unix shell syntax that does not work in Windows PowerShell. Solution: The test script in package.json was updated to use && for cross-platform sequential execution.

Chapter Five: Conclusion and Future Work

5.1 Conclusions

This project has successfully designed, implemented, and verified FURKO — a full-stack civic-technology platform for community problem reporting and resolution in Jimma City, Ethiopia. The platform meets all fifteen functional requirements and all eight non-functional requirements defined at the outset of the project. The 100% pass rate across 141 automated tests provides a high degree of confidence in the correctness, security, and reliability of the implemented system.

The core technical contribution of the project — the PostGIS geospatial automatic routing engine — functions correctly for all test cases, including spatial boundary matching, category-based routing, and out-of-bounds fallback handling. This engine eliminates the need for manual report dispatching and directly addresses the misrouting problem identified in the requirements analysis.

The institution-scoped RBAC system ensures that institution staff can only access reports, team members, and data belonging to their own institution, while the system administrator retains platform-wide visibility. The full audit trail in the status_history table creates accountability for every decision made about a report, from initial submission through to citizen-confirmed resolution.

The platform's architecture — containerized with Docker, built on open-source technologies, and deployed on a local network — makes it practical for a municipality with limited cloud infrastructure investment, and extensible to additional institutions or cities with only database configuration changes.

5.2 Achievements and Contributions

  • Designed and implemented the first digitized, full-lifecycle civic reporting platform tailored for Jimma City's institutional structure.
  • Implemented a PostGIS spatial routing engine that accurately routes reports to the correct institution based on GPS location and problem category.
  • Achieved 141/141 automated test pass rate, covering evidence validation, spatial routing, resolution lifecycle, RBAC security, and HTTP security headers.
  • Delivered three integrated platform components (mobile citizen app, web institution portal, REST API backend) as a cohesive, containerized system.
  • Established a detailed audit trail for every report action, providing the accountability infrastructure necessary for institutional adoption.
  • Produced comprehensive project documentation meeting the INSA 5th Cyber Talent Batch submission requirements.

5.3 Limitations

  • Version 1.0 does not include push notifications or SMS alerts; citizens must actively open the app to check report status updates.
  • The platform requires a functioning internet connection; offline report drafting is not supported in version 1.0.
  • The jurisdiction boundary polygons seeded in the database are approximations based on available GPS reference points and may not precisely match the official administrative boundaries of Jimma City's service institutions.
  • The platform currently supports only Amharic-locale English; Afaan Oromo and Amharic language interfaces have not been implemented.
  • The development deployment uses a local area network setup; a production deployment would require a cloud server with a domain name, HTTPS certificate, and reverse proxy configuration.

5.4 Recommendations and Future Work

  • Push Notifications: Integrate Expo Push Notifications (via Expo's push service or Firebase Cloud Messaging) to deliver real-time status update alerts to citizens when their report status changes.
  • SMS Notifications: Integrate with Ethio Telecom's SMS API to deliver tracking number confirmations and status updates to citizens via text message, reducing dependency on a smartphone.
  • Offline Report Drafting: Use expo-sqlite or AsyncStorage to allow citizens to compose reports offline, then automatically sync when connectivity is restored.
  • Multilingual Interface: Add Afaan Oromo and Amharic language support using React Native's i18n-js or expo-localization, making the platform accessible to Jimma City's primary language communities.
  • AI-Based Priority Classification: Train a lightweight NLP model on submitted report descriptions to automatically classify priority (high/medium/low), reducing manual prioritization by institution staff.
  • Geographic Expansion: The routing engine is designed to support multiple cities. Adding Jimma's surrounding towns or other Oromia Region cities requires only new routing rule and institution records in the database.
  • Production Deployment: Deploy the backend API and database on a cloud VPS (such as an AWS EC2 or a local Ethiopian cloud provider), configure HTTPS with a Let's Encrypt certificate, and publish the React web portal to a static hosting service. Publish the mobile app as an APK for distribution via QR code or a government app portal.
  • Analytics Dashboard: Build an admin analytics dashboard showing report volume by category, average resolution time by institution, spatial heat maps of reported problems, and citizen satisfaction rating trends.
